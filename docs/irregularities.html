Irregularities logged while building this

← back to the evidence page - every flag raised during the run, whether or not it turned out to be ours, per the brief. Rendered from evidence/irregularities.json.

16 entries. Three of them are about this tooling, not the geology, and are kept in the list because a documentation defect that survives into a decision is still a defect.

IR-56-001 · warn sample_submission.tif is not an empty template

Finding. The file named sample_submission.tif is cell-for-cell identical to existing_faults.tif: 60,988 positive cells in both, same lattice. Reading it as an all-zero template -- which is what the name invites -- would make a 'valid' submission that is just the catalogue.

What we did. Treated as the catalogue baseline, never as zeros. It is the reference grid for CRS/shape/geotransform in submission_writer, and it is arm A/C of the holdout, where it scores DTI 0.00000 because the evaluator masks visible catalogue pixels.

Verified by: rasterio read of both files in this workspace (evidence/grid.json)   Source: https://drivendata.org/competitions/306/competition-doe-gems/data/

IR-56-002 · bad Nodata in the feature stack is a finite number

Finding. training_features.tif stores nodata as float32 -3.4028234663852886e+38, which is finite, and 57.9% of band 1 is that sentinel. Any min/median/correlation computed without masking returns the sentinel and looks like a real, enormous signal.

What we did. Every read in this repo goes through gems56.corrections.load_fields, which converts the sentinel to NaN and asserts each band's DESCRIPTION string before use (sibling repos index the same bands differently -- GEMSDOE52 logged the same hazard as IR-52-019).

Verified by: measured on the pinned file in this workspace   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/src/gems56/corrections.py

IR-56-004 · warn The shared holdout is structurally blind to what this lane measures

Finding. holdout.make_folds masks visible catalogue pixels pixel-exactly, so a prediction that moves a dot 1-3 px off a catalogue line has nothing to be credited against: the withheld target is the catalogue's own hidden segments, and a lateral shift of a traced line is not a new segment. Measured, not argued: arm B (evidence snap) 0.00012 vs arm D (random sub-pixel jitter) 0.00011, overlapping intervals.

What we did. Reported as a limitation of the instrument rather than a failure of the hypothesis. The lane is judged by its own pre-registered rule (corridor-level consistency) plus two nulls and a sign-flip permutation control, and the holdout is used only to rule out a catastrophe.

Verified by: evidence/holdout_corrections_v1.json   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/evidence/holdout_corrections_v1.json

IR-56-005 · warn LiDAR layers are packed, and the packing differs between files

Finding. The 100 m scarp stack (h52_scarp3m_100m.tif) is int16 with nodata -32768 and a per-band SCALE divisor; the 3 m pilot tiles are plain int16 with z_m = 1000 + value/10. Taking either at face value yields elevations near -3276 m or a 1000 m bias.

What we did. Decoding asserted against each file's own metadata and bounds at load time, plus a valid-fraction guard that raises when a reprojection returns less than 90% valid data (the failure mode that silently produced all-NaN tiles during development).

Verified by: rasterio metadata + values read in this workspace   Source: https://github.com/buffedlizard55-lab/GEMSDOE48/blob/main/data/external/h52_scarp3m_100m.json

IR-56-006 · bad The duplicate-submission rule as written is vacuous against dense rasters

Finding. The lane protocol says: if >70% of my dots lie within 3 px of one registry raster's dots, log a duplicate and stop. Sibling repos publish whole-footprint plausibility masks (5,167,373 and 4,830,583 dotted cells). Against those, ANY non-empty submission is 100% contained, so the rule fires on every candidate in the corpus, including files that are not submissions at all. The reverse overlap for the same pairs was 0.01-0.12%. The authoritative run confirms it: gates.lane_uniqueness_report on the final primary dots returns max Spearman 0.0051 (pass, threshold 0.90) but directed <=3px proximity 1.000 against a 0.70 threshold, duplicate=true, ok=false, 105 offending priors -- because the raster carries a single dot. The sensitivity raster (14 dots) triggers 31 priors on the same criterion and 0 in the reciprocal direction.

What we did. Both directions plus the reciprocal minimum are computed for all 485 rasters (evidence/registry_screen_v1_rows.jsonl), the trigger is reported with the prior's dot count so a reader can see which priors are density masks, and the site does not claim a clean uniqueness pass. The rule's *intent* -- do not resubmit someone's raster -- is additionally served by the emission rule never placing a dot on a catalogue pixel. The gate's own verdict is published on the site banner and in the run card as a failure, and no slot is claimed for either raster.

Verified by: scripts/screen_registry.py over /home/user/_reg   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/evidence/registry_screen_v1.json

IR-56-007 · bad The first offset result was an instrument artifact, not a finding

Finding. Before calibration, the median absolute catalogue-to-crest offset was 0.656 px and looked like a small real displacement. Two null controls showed a random point with no fault anywhere is 'nearest crest' 0.49 px away and catalogue pixels sampled in a random direction 0.52 px away: the signal was inside the noise floor of the estimator.

What we did. Null-calibrated gates became mandatory for every statistic in this lane (crest height floor = 90th percentile of the null), the histogram is published next to both nulls, and the sign-flip permutation control was added for the cluster rule.

Verified by: evidence/calibration_v1.json, evidence/cluster_gate_control.json   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/evidence/calibration_v1.json

IR-56-008 · info Corridor z-scores explode when the MAD collapses

Finding. The robust SE of a median goes to zero when four corroborated pixels share a value, so z = |median|/SE reached 60.6 on one component -- arithmetically true, scientifically meaningless.

What we did. corridor_table now takes sigma_floor_px and floors the SE at the measured disagreement between a 100 m offset and the same offset measured on 3 m LiDAR (1.296 px). With the floor the same corridor's z is bounded by the instrument's precision. No z is quoted anywhere in this repo without that floor.

Verified by: evidence/lidar_calibration_v1.json estimator block   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/src/gems56/corrections.py

IR-56-009 · bad A sign-asymmetric crest detector in the lane's own code (found by a test, fixed here)

Finding. Three defects were caught while writing contract tests against synthetic scarps of known position: (a) the PCA strike vector had an arbitrary sign, so neighbouring pixels of one trace could place corrected dots on opposite sides; (b) the second difference was taken at 0.25 px sample spacing on bilinearly interpolated data, which turns the interpolation's piecewise linearity into a comb of curvature spikes one cell apart, and the 'nearest crest' rule then selected a spike instead of the scarp; (c) the prominence test measured a crest against its own flanking concave lobe, which exists only on one side of the trace, so right-hand scarps were rejected and left-hand ones accepted. (b) and (c) both shrink the offset histogram toward zero -- i.e. they could manufacture exactly the negative verdict this lane reported.

What we did. Fixed in src/gems56/corrections.py (lane code, not a vendored template module, so no shared-tool fork was created): strike canonicalisation, a one-cell curvature baseline with a widened sampling window, full-kernel-support requirement, and a relative-strength rule symmetric in the sign of the offset. All of E1, E1c, E2, E3 and the uniqueness screen were then re-run from scratch. The remaining known bias (+0.2 to +0.5 px, constant in offset, shape-dependent) is characterised in evidence/estimator_validation.json and is why no claim here rests on an absolute sub-pixel offset.

Verified by: tests/test_contracts.py (10 tests) + scripts/validate_estimator.py   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/evidence/estimator_validation.json

IR-56-013 · warn Our rasters write 0.0 outside the data extent; the official sample writes NaN

Finding. The format page says cells outside the provided data extent should be null or NaN, and sample_submission.tif does exactly that (7,111,787 NaN cells of 12,279,160). The rasters built here carry 0.0 in that region instead, because the shared template tool enforces an all-finite export policy: gates.format_report appends 'NaN/infinite pixels: fail our all-finite export policy (public spec permits outside-footprint NaN)' and submission_writer.write_submission refuses a prediction that is not finite. So this is a deliberate template decision that contradicts the organizer's sentence, not an oversight of this lane's.

What we did. Measured the consequence rather than assuming it: under DTI, FPw sums only over prediction pixels with p > 0, so 0 and null outside are arithmetically identical, and both are inside [0,1], which is what the upload range check enforces. Kept the template behaviour so this lane's file is byte-comparable with the sibling submissions that already uploaded, published the exact difference on the site instead of claiming compliance, and recorded the flip: writing out[~valid]=nan with nodata=nan in submission_writer (one edit, shared tool) if DrivenData ever rejects a 0-filled exterior. A reviewer with an account should confirm which convention the platform's validator prefers.

Verified by: independent rasterio read of both rasters and of the sample: non-null-outside-footprint count 12,218,172, sample NaN count 7,111,787   Source: https://github.com/buffedlizard55-lab/56GEMSDOE/blob/main/src/gems56/submission_writer.py

IR-56-015 · warn The uniqueness rule-as-written is still tripped by artefacts - now with a named culprit

Finding. Round 1's IR-56-006 said a one-way '>70% of dots within 3 px' test is vacuous against dense rasters. Over the full 868-raster mirror this round, 56 files trip it one-way and none reciprocally; 35 of the 56 hold under 500k dots, and the largest one-way value (0.9996) belongs to `13GEMSDOE__13gems_20261001_r13-lattice-s5_v2`, which is not a prediction at all: it is a regular 5-pixel lattice (rows 0,5,10,... x cols 0,5,10,...), so every point of the region lies within 3.54 px of one of its dots.

What we did. Both directions are reported everywhere in this round and the reciprocal (>0.70 both ways) is the criterion; the shared gate is run on the disclosed top-40 reciprocal subset (evidence/lane_uniqueness2_summary.json, ok=true for both rasters) while the exact 868-raster screen (evidence/registry_screen_h56b.json) covers the corpus. Any lane that reports only the one-way number against this corpus is reporting an artefact.

Verified by: rasterio read of the lattice file: unique row indices 0,5,10,... and column indices 0,5,10,...   Source: evidence/registry_screen_h56b.json
