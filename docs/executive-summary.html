Executive summary

One page: what to download, how to file it, what this run proved, and what it rules out.

Downloadable, format-valid, and not cleared for a slot by this run

Downloading is safe: both rasters are in the submission format, values in [0, 1], null outside the footprint, validated after writing. Submitting spends one of the three weekly slots and buys an expected 0.00016 DTI (95% CI [0.00000, 0.00045]) against 0.00000 for submitting nothing at all. Filing it once is a legitimate way to record a negative on the scoreboard — it is not a way to beat 0.3195, and this run does not recommend it as one.

How to submit, exactly

  1. Download the primary .tif (1 dots) or the 1 px sensitivity .tif (14 dots). The .zip beside each holds the same single band; either is accepted.
  2. Sign in at drivendata.org/competitions/306 and open the Submissions tab. This competition accepts a file upload; no kernel is required.
  3. Pick a short submission name and paste the one from the download card, so the scoreboard row carries the label. Then upload. Do not re-save the file in a GIS or let a viewer strip its geotransform: the form requires the CRS (EPSG:32611), shape (3730×3292), 100 m pixel size and bounds to match the submission format exactly.
  4. Paste the note (the form allows one, ≤140 characters). Ours states the verdict, so a future reader of the scoreboard sees "NEGATIVE" next to the row rather than a mystery.
  5. Wait for the receipt. Until the platform returns a score, this page claims none: a projection is never written as a score.

Why earlier uploads were rejected, and why these will not be

The error Predicted values must be in range [0, 1] comes from a raster whose band holds a confidence-like quantity that is not a probability — log-odds, a 0–255 mask, or an int8 catalogue written straight out. It is a validator on the uploaded values, not on the geometry. These files were produced by the shared submission_writer and re-read after writing: the distinct values present are 0.0, 1.0 (primary) and 0.0, 1.0 (sensitivity), the validator reported no problems. One difference from the official sample, stated rather than hidden: the sample leaves everything outside the data extent as NaN, while these rasters fill it with 0.0, because the shared writer enforces an all-finite export policy (gates.format_report fails a file containing NaN and notes that the public spec permits it). Under the metric this cannot matter — FPw sums only over pixels with p > 0, so a 0 outside is arithmetically identical to a null — and 0 is in range, which is what the upload validator checks. Logged as IR-56-013, with the one-line change that flips it if the platform ever objects.

If the goal is to beat 0.3195, the next move is elsewhere — and this run says why

  • Mass on the catalogue is worth nothing. Staff-confirmed masking, plus a measured sibling result (0.2708 → 0.2778 from deleting exactly the 2,545 catalogue-adjacent dots). Every emission rule in this repo encodes that: no dot on a catalogue pixel.
  • The geometry rewards sparse, confident coverage of unmapped lineations. With α = 0.2, β = 0.8 and a 300 m kernel, a dot within 3 px of a truth pixel already earns partial credit, a missed truth pixel costs 0.8, and a false dot costs 0.2 — so the marginal value is in places with no candidate at all, not in sharpening places that already have one.
  • Registration is now ruled out as the explanation for a mediocre score, which is the useful product of a diagnostics lane: three candidate mechanisms (catalogue displacement, tail-only displacement, catalogue sharpening) are closed or declared untestable here, and effort can move to discovery and to fusion.
  • What would change this lane's mind: 1 m LiDAR over a corridor that qualifies even in the ungated table (component 2754 is the best candidate at -3.17 px), or a shifted-label instrument that can see a 2 px move at all.
