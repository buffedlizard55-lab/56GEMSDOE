The portal error "Predicted values must be in range [0, 1]" - why it happens and why these files do not

Two distinct defects produce that one message. (1) the official feature stack stores nodata as -3.4028234663852886e+38: a raster written from it without replacing the sentinel carries values far outside [0,1]; (2) a nodata tag holding that same sentinel is rejected even when the cell values are legal. The competition's own format section also permits null/NaN outside the bounds, so a file can be legal and one validator change away from rejection. Both rasters here are written all-finite with nodata=None, verified by re-opening the bytes on disk (docs/downloads/checks-*.json), and the sibling group's single best-scoring file - the one whose name ends -zeros - is exactly the all-finite twin of a NaN-carrying file, which is why that suffix is in its name. -zeros is not a zero prediction: the file holds 37,654 cells at value 1.0 (measured, not assumed).

Why the group's best file scored 0.2778, and what beating it takes

We were asked to explain the top result and to beat it. The explanation is a measurement, not a story. The sibling file h33-h33-2-b2-…-zeros (claimed 0.2778) is a strict subset of the file that scored 0.2600: 37,654 of its dots appear in the earlier raster, and the 6,436 deleted cells are exactly the dots within 2 px of a catalogue pixel (measured distance floor of the survivor: 2.24 px; share of the base file inside 2 px: 14.60%). No new detector, no retraining, no change of area: the whole gain of +0.0178 came from deleting mass that the organiser's mask makes worthless. That is the corrections lane's finding seen from the other side - the catalogue is accurate, so anything touching it is already known.

Because known-fault pixels are masked out of the truth while the 300 m kernel still discounts nearby false positives, the metric collapses to DTI = T / (0.2 (T + F) + 0.8 |G|). Two published scores and two measured dot counts then fix the rest: T = 5,223 credit for 37,654 dots (0.139 per dot) and |G| ≈ 12,783-18,294 hidden pixels. If placement were perfect at the same mass the same file would score 0.825. So the headroom is almost entirely credit per emitted pixel - better place-finding - not budget, not nodata handling, not the loss:
